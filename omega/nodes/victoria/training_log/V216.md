## Hypothesis

**Thread the current bar's UTC timestamp into the two sizing-side time-of-day sites in

## Implementation choice (pre-registered): bar-time param threading, gated on frozen mode

**Decision: explicit param threading, NOT a global `replay_now()` shim.** Rationale
(per the task brief's "fewer surprises, easier to audit"): both target functions
*already accept a time argument* —
- `core/risk_manager.py:316` `time_risk_multiplier(now: datetime | None = None)` —
  already defaults to `datetime.now(UTC)` when `None`. **No signature change needed.**
- `core/risk_manager.py` `apply_all(..., now=None)` already forwards `now` to
  `time_risk_multiplier`. **No signature change needed.**

So the entire threading change lives at **one file, `strategy.py`**:
1. New helper `_backtest_now_ts(market_data) -> datetime | None`: returns the latest
   bar timestamp (`market_data[sym]["timestamps"][-1]`, unix seconds → UTC datetime)
   **only when `OMEGA_FROZEN_CACHE=1`**; returns `None` in live mode.
2. Damp site (`strategy.py:2098`): `_hour_utc = (_bar_now or datetime.now(UTC)).hour`.
3. `apply_all` call site (`strategy.py:3364`): add `now=_bar_now`.

**Why gate on `OMEGA_FROZEN_CACHE`** (auto-set by `--backtest-snapshot`, the same gate
V215's HTTP guard and the new tripwire use): live trading legitimately wants real
wall-clock for genuine intraday risk windows. Gating on frozen mode makes the **live
path byte-unchanged** (`_bar_now` is `None` → both sites fall back to `datetime.now`,
exactly as today) and confines the new behavior to backtests.

### ⚠️ Daily-bar consequence (EXPLICIT — read before comparing any number)

The trend snapshot (`snap_trending_2023q4.json`) is **daily bars stamped at 00:00:00
UTC**. Under bar-time threading every cycle resolves to **hour=0, minute=0**, so:
- `time_risk_multiplier` → inside the `00:00–01:00` window → **0.75×** on every bar.
- damp window `{22,23,0}` → hour 0 ∈ set → **0.50×** `sit_out_size_mult` on every bar.
- Compounded: **~0.375× sizing uniformly on every bar.**

This is **deterministic** (the gate's goal) but a real, large baseline shift vs V215's
*no-window* replicates (which had `time_risk_mult=1.0` because the V215 runs executed
outside the windows). **Three things make this the correct call for V216:**
1. **Determinism is V216's job; "should intraday windows fire on daily bars" is a
   separate strategy question** (parked for V217). Smuggling a window-disable into a
   determinism fix would conflate two bets — exactly the silent-bundling failure mode
   the skill warns against. Bar-time threading is the minimal, faithful mechanism the
   task specified: "evaluate the window against snapshot time, not run time."
2. **The selector verdict is robust to a uniform multiplier.** ON vs OFF Δ is measured
   on the SAME 0.375× baseline; both arms get the identical factor, so the Δ isolates
   the selector. Absolute magnitudes scale; sign/relative comparison holds.
3. **It is honest and visible.** Whatever the hermetic strategy does under bar-time, the
   determinism gate (cheap, step 5) surfaces the trade counts before the expensive
   audit. If 0.375× collapses trades below the gate's count floor (≥20), that is
   reported, not hidden, and motivates a V217 "gate intraday windows on bar cadence"
   strategy change.

**FORK recorded (no AskUserQuestion per task):** the alternative was to *neutralize* the
intraday windows in frozen mode (mult=1.0), which would keep the baseline continuous
with V215's clean no-window numbers (−$7,880 ON / +$14,110 OFF). Rejected for V216
because it bundles a strategy change (windows shouldn't fire) into a determinism fix.
If the V216 audit shows a degenerate low-trade baseline, **V217 should evaluate cadence-
gating** (`apply intraday windows only when bar cadence < 1 day`) as an explicit,
pre-registered strategy bet. The V216 fence stands either way — it makes the eval
deterministic; the window-firing policy is orthogonal and revisable.
