## Why V206b exists

REFLECTION_V205.md (committed `9fb04f1`) found two facts that block any
further strategy edits:

1. The V172 "architecture stack" V204 restored is **code-present but
   runtime-inert** under `v93_baseline`: `strategy_selector_enabled`,
   `regime_signal_weighting`, `per_regime_ic_weighting`,
   `live_signal_normalization` all default `False` and are not set
   by any preset, config, or training script. The "V156 strategy_selector
   initialised" INFO line is absent from V204 and V205 logs.
2. Despite (1), V205's pre-registered no-op edit
   (`_REGIME_SIGNAL_WEIGHTS["CRISIS"] = {}` — a dict that is never read
   under v93_baseline) moved crisis PnL by +$14,277σ vs V204. The
   eval has hidden state coupling and we have been reading dict-edit
   noise as architectural signal for six versions (V199–V205).

V206b's job is **not** to fix the leak. Its job is to **locate** it.
Until we know what couples runs together, every PnL delta we measure
is contaminated by that coupling at unknown amplitude.

## Hypothesis

**Identical `strategy.py` + identical `--seed 42` + identical
`--backtest-snapshot` should produce byte-identical artifacts across
two sequential runs.** Any artifact that differs locates a state-leak
channel.

Artifacts in scope (whichever exist after a real run):

- `data/v206b_<gate>_<run>_results.json`
- `data/v206b_<gate>_<run>_trades.csv`
- `/tmp/v206b_<gate>_<run>_metrics.jsonl`
- `data/omega_victoria_state.db` (244K, sqlite — likely accumulates)
- `data/omega_victoria_memory.db` (76K, sqlite — likely accumulates)
- `data/decision_traces/<...>.jsonl` if `DecisionWriter` is wired for this version

The persistent sqlite DBs are the most suspicious channel:
`run_training.py:195` uses `data_dir / "omega_victoria_memory.db"`
and the file is 76K *now*, before V206b runs — meaning prior training
runs have left content there. If `StrategyNode.__init__` reads from
that file, the second run starts from a different state than the
first.

## Procedure

For each gate ∈ {recent, trend, crisis}:

1. Record a pre-run fingerprint of the persistent state:
   `sha256sum data/omega_victoria_state.db data/omega_victoria_memory.db`.
2. Run #1:
   ```
   python3 scripts/run_training.py \
     --version v206b_<gate>_r1 \
     --cycles 200 --sleep 10 --seed 42 \
     --backtest-snapshot data/snapshots/<snap>.json
   ```
3. Snapshot artifacts and the post-run sqlite files into
   `data/v206b_audit/<gate>_r1/`.
4. Run #2: same command with `--version v206b_<gate>_r2`. Same seed.
   Same snapshot. Identical strategy.py (no edits between runs).
5. Snapshot artifacts and sqlite files into
   `data/v206b_audit/<gate>_r2/`.

Snapshot file mapping (per V204/V205 logs):
- recent → `data/snapshots/snap_20260414.json`
- trend → `data/snapshots/snap_trending_2023q4.json`
- crisis → `data/snapshots/snap_crisis_2022h1.json`

All six runs are sequential — never overlapping — because parallel
runs would contaminate the shared sqlite DBs and obscure exactly the
signal we're trying to measure.

## Falsifiers (operational)

A divergence is **real** if:

- `cmp -s` returns non-zero between r1 and r2 of the same gate for
  the same artifact, AND
- For trades.csv specifically: the 5 spot-checked rows at the same
  `(cycle, symbol, side)` keys show different `pnl` values.

A divergence is **not real** if it only appears in timestamp fields
that are *purely* observational (e.g. `run.date`, `elapsed_s`,
`avg_cycle_s` in `results.json`). Those are wallclock artifacts and
do not constitute a state leak — they just need to be excluded from
the comparison.
