This is a **distinct** channel from V217's (Apple vecLib BLAS parallel-reduction

which is exactly why V217's 6/6 "byte-identical" eval missed it (0+0+…=0 is
order-insensitive; real dxy/yield_curve terms re-introduced non-zero

`trend_OFF` is the one boundary-adjacent cell where the sub-ulp noise flips a
single trade (27↔26 → $597). `recent_OFF` carries the **identical** $6.52 noise
with an unchanged 22/22 trade count — direct proof it is the same sub-ulp source,
not a larger channel, just crossing no decision boundary.

**Bet:** replace the order-sensitive `sum(...)` reductions in the `basic_signals`
composite path with **`math.fsum(...)`** (exact-rounded; returns the correctly-
rounded sum independent of input order → eliminates the order channel for free,
no stable-key sort needed). Pure eval-substrate fence; **no strategy change**,
live path byte-unchanged.

## Implementation choice — `math.fsum` over canonical-sort

Two options were on the table (V219 next-steps):
- **(a) canonical-sort** the composite contributors by a stable key before summing
  (the V211 basket_std/mean pattern), or
- **(b) `math.fsum`** the reductions.

Chose **(b)**. `fsum` is exact-rounded — it computes the full-precision sum and
rounds once, so the result is identical regardless of input order *without* needing
to invent or maintain a stable sort key. It is the surgical, lowest-churn fix and
the most robust (closes *any* permutation, not just the one we sorted against).

**Sites fenced (the active basic_signals composite reduction path):**
- `omega/nodes/victoria/victoria_node.py:960` — `raw_value = sum(composites)/len(composites)`
  the per-ticker→cross-ticker mean that *directly* produces `basic_signals.value`
  (the named divergent field). Primary site.
- `omega/nodes/victoria/signal_generation.py:_balanced_composite` (178, 181) — the
  per-ticker composite reduction that feeds `composites`. (The IC-weighted path

  → falls back to `_balanced_composite` — so it is out of scope here; V221 will

## Methodology lesson — the FP-order audit pattern (third precedent)

V220 is the **third** time we have closed a floating-point summation-order channel
in this eval:
- **V211** — `basket_std` / `basket_mean` cross-sectional aggregations
  (`strategy.py:1722`/`:2130`) → two `sorted()` wraps.
- **V217** — Apple vecLib BLAS multi-threaded parallel-reduction order → pin BLAS
  to 1 thread before numpy load.
- **V220** — `basic_signals` composite mean → `math.fsum`.

Three precedents is a pattern, not a coincidence. **Skill update queued** (Step 8):
add an "FP-order audit pattern" section so future iterations, when a determinism
gate fails, **grep for unsorted FP summations (`sum(` / `+=` over dict/set/list
iteration of floats) as the default first check** before any deeper bisect.
